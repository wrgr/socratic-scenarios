# Rebuilding the AJP corpus

A playbook for removing and recreating the corpus from scratch (or adding new
sources to it) without repeating the sensitivity gaps found and fixed in
July 2026 — see that cleanup's commit for the full incident: a personal file
path baked into ~20 files, a third party's username shipped in the public
corpus, and raw machine-configuration data (real IPs, camera serial numbers, a
COM port, real recipe filenames) from a live deployment.

Run everything below **locally** — this doc assumes you have file access to
your own source documents, which a cloud/sandboxed session will not.

## The two corpora — don't confuse them

TeachMe has two independent knowledge stores. Rebuilding one doesn't touch the
other.

| | Knowledge graph | Dense-retrieval corpus |
|---|---|---|
| **What** | Hand-authored typed nodes/edges (faults, steps, hazards, tacit knowledge, probes) | Chunked + embedded document text for semantic search |
| **Where** | `src/corpus/ajp/*.ts` | `public/ajp-corpus.json` |
| **How it's built** | You write TypeScript directly | Generated by a script from real documents |
| **Powers** | Scenario Mode, Socratic Practice, Narrator, Retrieval Lab's graph tier | Reachback Lookup's dense tier, Retrieval Lab's corpus browser |
| **Citations** | `SRC-###` (external) or `KB-DOC-##` (internal) in `source:`/`content` fields | `source` + `section` per chunk, from the ingestion manifest |

**Only one ingestion pipeline is actually live.** The codebase has two:
`scripts/ingest-corpus.ts` (`npm run ingest`, no database) and a parallel
SQLite-backed pipeline (`npm run db:full-setup` → `db:export`) that both
write to the same `public/ajp-corpus.json`. As of this writing,
`knowledge/knowledge.db` doesn't exist in the repo — `npm run ingest` is what
actually produced today's corpus. Don't run the `db:*` pipeline expecting it
to reconcile with `npm run ingest`'s output; treat migrating to the
DB-backed pipeline as a separate, deliberate decision, not something to mix
mid-rebuild.

## Before including *any* source — the sensitivity checklist

Classify every candidate source before it goes anywhere near
`ACTIVE_SOURCES` or a graph node's `source:` field:

1. **Is it published, public content?** (peer-reviewed paper, government
   guidance, vendor marketing page, officially-numbered vendor manual/PDF) →
   safe to include. Cite it properly (`SRC-###` in `source-ref-registry.ts`
   for external docs).
2. **Is it vendor-provided but *not* one of the official numbered
   manuals** (an emailed PDF, an informal Q&A doc, training notes someone
   sent you)? → **hold.** Confirm redistribution rights before including it
   publicly. When in doubt, exclude (see below) rather than guess.
3. **Is it exported from a real, live deployment** — machine configuration,
   network settings, log files, recipe/toolpath files, camera or device
   serial numbers? → **exclude the raw file.** If the underlying knowledge is
   generally useful (e.g. "this alarm means X"), hand-author an abstracted
   graph node instead of ingesting the raw export — see
   `src/corpus/ajp/design-faults.ts`'s `FAULT-BUBBLER-TEMP-*` nodes for the
   pattern: real alarm knowledge, zero real device addresses.
4. **Does the file's path, front-matter, or body contain anyone's username,
   home directory, email, or a real facility's identifying details?**
   Scrub it — see "Personal-path hygiene" below — regardless of how you
   classified the content itself.
5. **Does it reveal a specific ink/material/process choice as if it were
   universal, when it's really one site's choice?** That's fine as a
   **flagged baseline** (see `PARAM-INK-IDENTITY-001` in `parameters.ts` for
   the pattern), never as an unqualified fact.

When a source fails this checklist, don't just leave it out silently — add
it to `EXCLUDED_SOURCES` in `scripts/ingest-corpus.ts` with a one-line
reason. It'll show up in the app's Domain Sources panel (References &
Whitepaper → Domain Sources → "Excluded — sensitivity review") automatically.

## Personal-path hygiene

Never put an absolute path like `/Users/yourname/...` in anything that gets
committed. `scripts/ingest-corpus.ts`'s `ACTIVE_SOURCES` uses paths relative
to a gitignored `local-sources/` directory instead
(`./local-sources/oem-manuals/9001094-motion-vision-kewb.pdf`) —
follow that pattern for any new local file. See `local-sources/README.md`.

## Rebuilding the dense-retrieval corpus

1. **Wipe the slate (optional).** To start genuinely clean rather than
   incrementally editing:
   ```bash
   rm public/ajp-corpus.json public/ajp-node-embeddings.json
   ```
   The app degrades gracefully without these — dense tier and node-embedding
   cache just report unavailable until you regenerate them.

2. **Populate `local-sources/`** per `local-sources/README.md` — one file per
   `ACTIVE_SOURCES` entry that has a `localPath`. Entries with a `url` fetch
   automatically; you don't need local copies for those.

3. **Review `scripts/ingest-corpus.ts`'s `ACTIVE_SOURCES` and
   `EXCLUDED_SOURCES`** before running anything:
   - Remove any entry whose source you no longer have rights to use.
   - Add new entries only after they pass the checklist above.
   - If you're re-adding something previously excluded (e.g. you've now
     confirmed Optomec's redistribution rights for the "HD2 Documentation"
     trio), move it from `EXCLUDED_SOURCES` to `ACTIVE_SOURCES` — don't
     duplicate it in both.

4. **Set your Gemini API key** (`VITE_GEMINI_API_KEY` in `.env` or the
   environment) and run:
   ```bash
   npm run ingest
   ```
   Watch the console output — it prints stub-source acquisition notes and
   the excluded-sources list before processing, and reports per-source
   chunk counts and any parse failures as it goes.

5. **Spot-check the output.** `public/ajp-corpus.json`'s `sourcesSummary`
   should show `"status": "ok"` with a chunk count proportional to the
   document's real length — a whole manual coming back as 1 chunk usually
   means a broken extractor, not a genuinely short document (this is exactly
   what happened with the old `Alarms.xml`/`Process_Configuration.xml`
   entries before they were excluded).

6. **Regenerate graph node embeddings** if you also touched the knowledge
   graph — `npm run ingest` does this automatically as its last step
   (writes `public/ajp-node-embeddings.json`).

## Editing the knowledge graph

There's no "rebuild" script for this side — it's hand-authored TypeScript in
`src/corpus/ajp/`. When adding a node:

- Give it a real citation: `SRC-###` (add to `source-ref-registry.ts` first
  if it's a new external source), `KB-DOC-##` (add to `kb-doc-registry.ts`
  first if it's new internally-authored material), or, if the knowledge came
  from direct observation of a real deployment you're choosing not to
  publish the raw source for, use the abstraction pattern: describe the
  generalizable knowledge in `content`, and write `source:` as something
  like `'Internal deployment observation (...) — raw source withheld from
  public corpus, see EXCLUDED_SOURCES in scripts/ingest-corpus.ts'`.
- Never embed a real device address, serial number, filename, or path in
  `content` or `source` — abstract it (a KEWB tag name like `ATM_MFC` is
  fine; a real IP or COM port is not).
- If you're deliberately choosing a default/baseline for something the
  corpus doesn't actually know for certain (an ink, a substrate, a
  parameter), say so explicitly in the node's own `content` — see
  `PARAM-INK-IDENTITY-001` — and track it as a gap in `corpus-gaps.ts`
  rather than asserting it as fact.

## Verifying the rebuild

```bash
npm run lint
npm run test     # corpus-integrity.test.ts + source-integrity.test.ts
                 # catch dangling edges, dangling SRC-###/KB-DOC-## citations,
                 # and unfilled authoring-template placeholders
npm run build
```

Then open the app, go to **References & Whitepaper → Domain Sources**, and
confirm every source you added shows up in the right category (cited /
registered-but-not-cited / indexed / not-parsed / excluded) with the chunk
counts and citation counts you expect.
